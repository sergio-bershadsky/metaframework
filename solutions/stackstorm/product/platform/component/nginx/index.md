What a browser and a CLI actually connect to on the reference deployment. It
terminates TLS, serves the single-page application's built assets from disk, and
routes the API, authentication and stream paths to the three services that have
listeners — which is why an operator configures one URL rather than three ports.

The `depends-on` list is the gateway discipline's requirement read literally: it
names everything this component fronts, including the web UI whose files it
serves from another product's subtree.

## Why it is `gateway` and not `service`

It owns no behaviour. Every request it answers is either a file from disk or
somebody else's response, and there is no rule, no policy and no state in it
that belongs to this platform. That is the whole content of the `gateway` type,
and this is about as clean an instance of it as exists.

## Why it declares only one environment

This component describes the reverse proxy the project's own single-host
reference deployment configures. The other two targets in this catalog do not
have it:

- The compose deployment's service list contains no reverse proxy at all; the
  web UI's own container serves itself, and the ports are published directly.
- The clustered deployment's edge is a Kubernetes Ingress — a resource, matched
  to whatever ingress controller the cluster already runs. That controller is
  not a workload this solution deploys, and the survey behind this catalog did
  not establish which one it is, so nothing is claimed about it.

Stating one environment where three exist is the honest reading, and the gap it
leaves is itself informative: the edge of this system is a different thing in
each of the three shapes the project ships.

## What is deliberately not described

Its configuration. The virtual host, the certificate paths and the location
blocks are generated by the installer and differ per deployment; describing one
installation's file would be describing a deployment rather than the software.
