Everything a person can do to this platform arrives here. The web UI is a
client of it, the command line is a client of it, the chat bridge is a client of
it, and an integration holding an API key is a client of it. Behind the reverse
proxy it is one process; in front of it, it is the whole product.

The conversation is ordinary: JSON over HTTPS, a bearer credential in a header,
a versioned path prefix. What is not ordinary — and what earns this entity its
place in a catalog written to test an ontology — is the state of its own
description.

## Three spellings of every operation, and the artifact holds one

The project publishes an interface description. It is a **Swagger 2.0** document,
not an OpenAPI 3 one, so the framework's `openapi.yaml` role — whose dialect row
pins the `openapi:` key to `3.1.x` — cannot admit it as anything but a legacy
dialect, when it is in fact a different current industry standard.

Underneath that, the paths disagree three ways:

- the description says `/api/v1/executions`;
- the service serves `/v1/executions`, because it applies a transform table at
  start-up that rewrites the documented prefix;
- and the same table adds `/actionexecutions`, a legacy alias that appears in no
  description at all.

The reverse proxy reconciles the first two by stripping its own location prefix
before proxying. So a client and the service agree, a reader of the description
agrees with neither, and one live path is documented nowhere.

The mini-spec's `base-path` is a single string. This file writes the
operator-facing prefix, because that is the one a client types, and says here
that it is one of three.

## The description is generated, and the running service reads the other one

The checked-in interface description carries a header saying it is generated by a
make target from a template beside it. The service does not read it: at start-up
it renders **the template**, injecting four Python constants — among them the
fourteen live-action statuses that
[live-action](srn://stackstorm/datamodel/live-action@1) transcribes.

So the framework's assumption that `openapi.yaml` is an authored artifact,
addressable as `.openapi` and snapshotted with the entity, is false twice over
here: the addressable file is a build product, and the source of truth is a
template that the role table has no row for. A catalog that vendored the
generated file would be pinning a rendering of a contract whose inputs live in
the code the catalog also describes.

## Why there is no `openapi.yaml` in this directory, and what that costs

The description is a large body of somebody else's text under a different
licence. This repository is source-available under a noncommercial licence and
the surveyed project is Apache-2.0; vendoring one into the other is a decision
nobody has taken, so the file is cited and not copied.

The framework's own rule then bites. `spec` and a surface list are mutually
exclusive: either point at the real file, or write the lightweight list. With no
file to point at, the list is the only option — and the list below is a
**selection**, not an enumeration. The published description carries ninety-two
distinct paths; nine appear here, chosen because this catalog's journeys and
datamodels refer to them.

The mini-spec has no way to say that. A surface list is presented as the surface,
and a partial one silently understates the protocol. The framework's
anti-duplication rule was written for the case where a spec file exists; the case
where a spec exists and cannot be vendored produces a surface list that is
honest only because this paragraph is next to it.

## Two smaller shapes the operation object cannot hold

**A list response.** Half the operations here answer with an array of records,
and `response` names one datamodel. There is no cardinality field, so
`list-executions` and `get-execution` are indistinguishable in the artifact.

**Two credentials for one operation.** Every operation accepts either a token
from [auth-api](srn://stackstorm/protocol/auth-api@1) or a non-expiring API key,
and which one a caller used changes nothing about the request except the header
name. `auth` is a list of display labels, which is exactly the right shape for
this — recorded here as the one place the mini-spec's deliberate looseness was
better than a typed scheme would have been.
